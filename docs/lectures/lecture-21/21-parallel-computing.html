Using joblib for parallel computing

  • Each call to bar is independent, so the calls can run at once
  • Your CPU has several cores. Each runs one task at a time
  • joblib sends tasks to worker processes: separate copies of Python
  • Parallel(n_jobs=6) runs up to six tasks at once. n_jobs=-1 uses all cores
  • delayed(bar) wraps bar, so a worker runs it later
  • delayed(bar)(x) for x in foo is a generator expression: a for loop inside parentheses that makes one task per element
  • More information about joblib on their website: https://joblib.readthedocs.io/en/stable/
  • With bar and foo from before:
# Install joblib if you haven't done so yet
# !pip install joblib

from joblib import Parallel, delayed

results = Parallel(n_jobs=6)(
    delayed(bar)(x) for x in foo
)
results

Serial vs parallel execution

  • Our function calculation (below) runs ten heavy steps on ten million random numbers
  • The calls are independent, so the problem is embarrassingly parallel
  • %timeit averages a line over several runs (Jupyter only)
  • %%timeit (two % signs) times a whole cell
  • One call:
def calculation(size=10000000):
    # Create a large array and perform operations
    arr = np.random.rand(size)
    for _ in range(10):

  • _ names a loop variable we do not use

concurrent.futures

concurrent.futures: the standard-library option

  • concurrent.futures comes with Python: nothing to install
  • Computing (maths, model training): ProcessPoolExecutor
  • Waiting (downloads, API calls): ThreadPoolExecutor
  • Processes are separate copies of Python that compute at the same time
  • Threads share one copy of Python, so they start fast. While one waits, the others keep working
from concurrent.futures import ProcessPoolExecutor

with ProcessPoolExecutor(max_workers=4) as executor:
    results = list(executor.map(bar, foo))
  • In a notebook, import bar from a .py file. Workers cannot see functions defined in a cell, but joblib can
  • Threads start fast and need no extra core to wait
  • Each URL asks the World Bank API for one country’s population
from concurrent.futures import ThreadPoolExecutor
import requests

base = "https://api.worldbank.org/v2/country/"
end = "/indicator/SP.POP.TOTL?format=json&per_page=100"
urls = [base + "BRA" + end,
        base + "IND" + end,
        base + "USA" + end]

def fetch(url):
    return requests.get(url, timeout=30).json()

with ThreadPoolExecutor(max_workers=3) as executor:
    results = list(executor.map(fetch, urls))
  • All three requests wait at once (Lecture 19 sent one at a time)

Big O notation

Big O notation

  • Big O notation describes how runtime grows with input size
  • O(1) is constant: reading one array element takes the same time at any size
  • A single loop is O(n), linear: double the input, double the time
  • A nested loop is O(n²), quadratic: double the input, four times the time
  • Calling calculation n times is O(n): 100 calls take 100 times as long as one
Code 
import matplotlib.pyplot as plt
import numpy as np

# Simulate processing times
num_images = np.array([1, 10, 50, 100, 200])
sequential_time = num_images * 2  # 2 seconds per image
parallel_time = (num_images * 2) / 4  # 4 cores, ideal speedup

plt.figure(figsize=(8, 5))
plt.plot(num_images, sequential_time, 'o-', label='Serial O(n)', linewidth=2, markersize=8)
plt.plot(num_images, parallel_time, 's-', label='Parallel on 4 cores (still O(n))', linewidth=2, markersize=8)
plt.xlabel('Number of Images', fontsize=12)
plt.ylabel('Time (seconds)', fontsize=12)
plt.title('O(n) Scaling: Serial vs Parallel', fontsize=14, fontweight='bold')
plt.legend(fontsize=11)
plt.grid(True, alpha=0.3)
plt.show()

What parallelism does to complexity

  • With p cores, an O(n) task takes about n/p time plus overhead. It is still O(n)
  • Best candidates: embarrassingly parallel O(n) tasks, which share no data and do not wait for each other

Parallelism divides the time by a constant but never changes the Big O class. O(n²) on eight cores is still O(n²)

  • Parallelism cannot fix this:
# O(n^2): every pair of elements
def pairwise_sum(data):
    n = len(data)
    results = []
    for i in range(n):
        for j in range(n):
            results.append(data[i] + data[j])
    return results

data = list(range(1_000))
print(f"{len(pairwise_sum(data)):,} operations")
1,000,000 operations
  • 1,000 elements give 1 million operations
  • n = 100_000 gives 10 billion. Eight cores still leave 1.25 billion each
  • Poor candidates for parallelism:
    • Steps that need results from a previous step
    • Tasks that share the same data
    • Tasks limited by memory, not by the CPU

Appendix 01

Amdahl’s law

Amdahl’s law: the speed-up ceiling

  • Some parts of a program cannot run in parallel: setup, merging results, or steps that wait for the one before
  • That part is the serial share \(s\). The rest, \(p = 1 - s\), can be split across cores
  • More cores only speed up \(p\), so \(s\) sets a ceiling (Amdahl’s law)
  • \(\text{speedup} = \dfrac{1}{s + \dfrac{p}{N}}\), with \(N\) = cores
  • Example: 90% parallel (\(s = 0.1\)) on 8 cores gives \(\frac{1}{0.1 + 0.9/8} = \frac{1}{0.2125} \approx 4.7\times\), not \(8\times\)
  • With infinite cores, the limit is \(1/0.1 = 10\times\)
Code 
import matplotlib.pyplot as plt
import numpy as np

cores = np.arange(1, 65)
serial_fracs = [0.05, 0.2, 0.5]
labels = ["95% parallel", "80% parallel", "50% parallel"]
colours = ["#1B3A6B", "#E07A24", "#2CA02C"]

plt.figure(figsize=(8, 5))
for s, lab, c in zip(serial_fracs, labels, colours):
    speedup = 1 / (s + (1 - s) / cores)
    plt.plot(cores, speedup, label=lab, linewidth=2, color=c)

plt.xlabel("Number of cores", fontsize=12)
plt.ylabel("Speed-up (×)", fontsize=12)
plt.title("Amdahl's law: speed-up vs core count",
          fontsize=14, fontweight="bold")
plt.legend(fontsize=11)
plt.grid(True, alpha=0.3)
plt.tight_layout()
plt.show()

Dask

Dask

  • Dask is a Python library for parallel computing
  • It handles data bigger than your RAM and runs on clusters of many machines
  • You write NumPy or pandas code, and Dask runs it in parallel
  • A task scheduler splits the work into small tasks and spreads them over your cores
  • Dask offers arrays, DataFrames and bags (parallel lists)
  • Latest release: 2026.8.0 (August 2026)
  • Next lecture times the same group-by in DuckDB, pandas and Dask

https://www.dask.org/

joblib splits the work into function calls. Dask also splits the data into chunks, so the data can be bigger than your RAM

Dask delayed

Dask delayed

  • dask.delayed parallelises functions you already have
  • No Dask DataFrame or array needed
  • First, four calls in a row:
def calculation(size=10000000):
    arr = np.random.rand(size)
    for _ in range(10):
        arr = np.sqrt(arr) + np.sin(arr)
    return np.mean(arr)

%timeit [calculation() for _ in range(4)]
1.37 s ± 46.6 ms per loop (mean ± std. dev. of 7 runs, 1 loop each)
  • A decorator is an @ line above a def. It changes what the function does
  • With @dask.delayed, calling the function creates a task instead of running it
@dask.delayed
def delayed_calculation(size=10000000):
    arr = np.random.rand(size)
    for _ in range(10):
        arr = np.sqrt(arr) + np.sin(arr)
    return np.mean(arr)

results = []
for _ in range(4):
    results.append(delayed_calculation())

# Compute all results at once
%timeit final_results = dask.compute(*results)
510 ms ± 11 ms per loop (mean ± std. dev. of 7 runs, 1 loop each)
  • dask.compute(*results) runs all four tasks. * unpacks the list into four arguments

Dask delayed

  • Three functions on three input sizes: nine tasks in three branches
@dask.delayed
def generate_data(size):
    return np.random.rand(size)

@dask.delayed
def transform_data(data):
    return np.sqrt(data) + np.sin(data)

@dask.delayed
def aggregate_data(data):
    return np.mean(data)

# Build the tasks (nothing runs yet)
dask_results = []
for size in [1_000_000, 2_000_000, 3_000_000]:
    data = generate_data(size)
    transformed = transform_data(data)
    dask_results.append(aggregate_data(transformed))

%timeit dask.compute(*dask_results)
23.1 ms ± 636 μs per loop (mean ± std. dev. of 7 runs, 10 loops each)
  • dask.visualize() draws the plan without running it
# Needs graphviz: pip install graphviz
# plus brew/apt install graphviz
dask.visualize(*dask_results)

Best practices

Best practices

  • Measure first with %timeit. Amdahl’s law says what fixing the slow part is worth
  • Check that tasks are independent and big enough to be worth a worker
  • A better algorithm often beats parallel code on large inputs
  • A faster engine like DuckDB may beat parallel pandas (next lecture)
  • NumPy or pandas may already have a fast built-in function
  • Do you need all the data? Try a sample first
  • Our parquet group-by was about 10× faster than CSV
  • Call .compute() and .persist() rarely: each call runs the whole plan
  • Try a few chunk sizes, or start with chunks='auto'
  • More tips in the Dask best practices

The most common mistake is parallelising before measuring. More cores will not fix a slow disk or an \(O(n^2)\) loop

def square(x):
    return x**2

# Create a large array to process
numbers = np.arange(1000000)

# Sequential version
%timeit [square(x) for x in numbers]
44.6 ms ± 604 μs per loop (mean ± std. dev. of 7 runs, 10 loops each)
from joblib import Parallel, delayed

# Parallel version
%timeit Parallel(n_jobs=4)(delayed(square)(x) for x in numbers)
1.9 s ± 55.8 ms per loop (mean ± std. dev. of 7 runs, 1 loop each)
  • The parallel version is slower here
  • square(x) is so fast that sending a million tiny tasks to the workers costs more than the work
  • Parallel computing pays off when each task is heavy

Appendix 02: why medium chunks win

  • Every chunk becomes a few tasks, and each task has a fixed overhead: Dask plans it, sends it to a worker and collects the result
  • Small chunks (100): hundreds of tiny tasks, so most of the time goes on overhead
  • Large chunks (2): little overhead, but only 2 cores have work
  • Medium chunks (5): 5 cores busy, few tasks to manage
  • Auto aims for about 128 MB per chunk. Our 80 MB array becomes one chunk on one core
  • Best size: big enough that overhead is small, small enough that every core gets work
  • My laptop has 10 cores, so about 10-20 chunks would probably be faster still
