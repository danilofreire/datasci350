Dask Clients and Clusters 🌐

What is a Dask Cluster?

Workers and schedulers

  • A Dask Cluster is a group of computational engines (cores, GPUs, servers, etc.) that work together to solve a problem
  • Workers provide two functions:
    • Compute tasks as directed by the scheduler. The scheduler is the brain of the cluster
    • Store and serve computed results to other workers or clients
  • Workers are the reason why lazy evaluation speeds up computations
  • Here is a simple example:
Scheduler -> Eve: Compute a <- multiply(3, 5)!
Eve -> Scheduler: I've computed a and am holding on to it! 
Scheduler -> Frank: Compute b <- add(a, 7)!
Frank: You will need a. Eve has a.
Frank -> Eve: Please send me a.
Eve -> Frank: Sure. a is 15!
Frank -> Scheduler: I've computed b and am holding on to it!

What is a Dask Cluster?

How the scheduler assigns work

  • How do workers know what to do?
    • The scheduler assigns tasks to workers based on their availability
    • Workers can be on the same machine or on different machines
    • Workers can be CPUs or GPUs
  • These processes can automatically restart and scale up without any intervention from the user
  • The optimal number of workers depends on data size and computation complexity
  • The default configuration is usually enough
  • In an adaptive cluster, you set the minimum and maximum number of workers
  • The cluster adds and removes workers as the work demands
  • Dask also provides a dashboard to monitor the performance of your cluster

Setting up a Dask Client

One client at the top of your script

  • Using dask.distributed requires that you set up a Client
  • This should be the first thing you do if you intend to use dask.distributed in your analysis
  • It offers low latency, data sharing between the workers, and is easy to set up
from dask.distributed import LocalCluster, Client

# Specify a different port for the dashboard
# Use fewer workers and threads to avoid resource issues
cluster = LocalCluster(dashboard_address=':8789', n_workers=2, threads_per_worker=2)
client = Client(cluster)

# Print the dashboard link
print(f"Dask dashboard is available at: {cluster.dashboard_link}")
Dask dashboard is available at: http://127.0.0.1:8789/status

  • Opening that link in your browser gives you the dashboard on the next slide

The single-machine renaissance 🚀

A reality check

“Big data” doesn’t only mean “buy a cluster”

  • For a decade, “big data” meant “buy a cluster”, and that assumption is now often wrong
  • A modern laptop has 8-16 cores and fast SSD storage
  • Most datasets that feel large (a few GB, tens of millions of rows) fit comfortably on one machine if the engine is written for it
  • Why does this matter for you?
    • No cluster to set up, pay for, or debug
    • Ordinary code, running fast
    • Enough for the final project and most real jobs
  • The old advice (“just use Spark”) often makes things slower at this size, because cluster coordination has real overhead
  • Two public benchmarks agree: Polars and DuckDB perform really well

Groupby on 5 GB, 16 cores and 32 GB RAM. DuckDB is one of the winners, and Polars does a great job too. Source: db-benchmark

Why single-machine engines got so fast

The design decisions Polars and DuckDB share

  • Columnar memory (Apache Arrow): data is stored column by column, so a query reads only the columns it needs, streaming through contiguous memory
  • Vectorised kernels: the heavy loops are written in Rust (Polars) or C++ (DuckDB), running in batches on your CPU’s SIMD instructions
  • All cores by default: every query is parallelised across your cores, with no cluster and no n_jobs to set
  • “Average one column” then reads a tiny slice of the file

Source: pola.rs/posts/benchmarks

Polars 🐻‍❄️

What is Polars?

The product page, before the syntax

  • Polars is a DataFrame library written in Rust
  • Its own headline is “DataFrames for the new era”
  • The numbers on the front page: 775 million downloads and 39,000 GitHub stars, under an MIT licence
  • It feels like pandas, with four differences:
    • The multi-threaded Rust engine uses all your CPU cores automatically
    • Data sits in Arrow columnar memory
    • A lazy mode optimises your whole query before running it
    • It can stream data larger than RAM
  • Install it with pip install polars

Source: pola.rs

# pandas
df["decade"] = (df["year"] // 10) * 10

Lazy mode: let the engine plan the query

Nothing runs until you call collect

  • scan_parquet returns a lazy frame: nothing runs until you call .collect()
  • This lets Polars reorder and prune your query like a database would
lazy = (
    pl.scan_parquet("../lecture-19/data/wdi_panel.parquet")
    .filter(pl.col("year") >= 1990)
    .group_by("indicator")
    .agg(pl.col("value").mean())
)
result = lazy.collect()
result.head(3)
shape: (3, 2)
indicator value
cat f64
"primary_enrolment_net" 87.585799
"gdp_per_capita" 14330.646062
"urban_pop_pct" 57.766502
  • .explain() shows the optimised plan:
print(lazy.explain())
AGGREGATE[maintain_order: false]
  [col("value").mean()] BY [col("indicator")]
  FROM
  simple π 2/2 ["indicator", "value"]
    Parquet SCAN [../lecture-19/data/wdi_panel.parquet]
    PROJECT 3/5 COLUMNS
    SELECTION: col("year") >= 1990
    ESTIMATED ROWS: 59024
  • Read the nodes bottom-up: Polars pushes the filter and the column selection down into the file scan, so it never reads data it will throw away
    • It’s like mean(filter(read(file))): the outermost call is written first but happens last
  • π is projection (keep these columns) and SELECTION is the row filter, two ideas from relational algebra
  • Polars reads 3 of the 5 columns and drops the old rows before any data reaches your query

Streaming: data larger than RAM

One argument changes how the query runs

  • The same lazy query can run in streaming mode
  • Polars processes the data in small batches, so the full dataset never sits in memory at once
result = (
    pl.scan_parquet("../lecture-19/data/wdi_panel.parquet")
    .filter(pl.col("year") >= 1990)
    .group_by("indicator")
    .agg(pl.col("value").mean())
    .collect(engine="streaming")
)
result.shape
(8, 2)
  • The only change is collect(engine="streaming")
  • This is how Polars handles files bigger than your RAM on a single machine
  • We use exactly this in the benchmark, on a file of 200 million rows

Note: the streaming engine has changed name across Polars versions. On Polars 1.43 (this deck) it is collect(engine="streaming")

Polars and pandas can work together!

Converting in both directions

  • You do not have to choose one forever
  • Convert in either direction:
# Polars -> pandas
pdf = result.to_pandas()

# pandas -> Polars
back = pl.from_pandas(pdf)
type(pdf), type(back)
(pandas.DataFrame, polars.dataframe.frame.DataFrame)
  • Typical pattern:
    • Do the heavy data work in Polars (fast, parallel)
    • Convert to pandas when a tool needs pandas: plotting with matplotlib, or feeding scikit-learn
  • The conversion is cheap because both use Arrow underneath

DuckDB 🦆

SQL as a scaling tool

The DuckDB home page, before the syntax

  • DuckDB is an in-process analytical database written in C++, and its own tagline is “Your universal data wrangling tool”
  • Think “SQLite for analytics”: no server, just pip install duckdb
  • Like Polars, it is parallel and out-of-core (it can process data larger than RAM)
  • Its trick: query files directly, with no loading step

Source: duckdb.org

  • Query a Parquet file straight from disk:
import duckdb

duckdb.sql("""
    SELECT indicator, AVG(value) AS mean_value
    FROM '../lecture-19/data/wdi_panel.parquet'
    WHERE year >= 1990
    GROUP BY indicator
    LIMIT 3
""")

Querying a DataFrame by name

Your Python variable becomes a SQL table

  • DuckDB can also query a DataFrame that already sits in a Python variable
  • The variable name becomes the table name in your SQL
import pandas as pd

pdf = pd.read_parquet(

# The variable `pdf` is now a SQL table
duckdb.sql("SELECT COUNT(*) AS n FROM pdf")

  • Full SQL works: GROUP BY, joins, subqueries, window functions
  • country is a pandas category, which DuckDB reads as an enum: ::VARCHAR turns it back into plain text so the result prints tidily
duckdb.sql("""
    SELECT country::VARCHAR AS country,
           ROUND(AVG(value), 1) AS mean_value,
           COUNT(*) AS n
    FROM pdf
    WHERE year >= 2000
    GROUP BY country
    ORDER BY mean_value DESC
    LIMIT 3
""")

When to use SQL

Choosing between expressions and SQL

  • Polars and DuckDB solve the same problems at similar speed
  • The choice is mostly about what you find readable:
    • Polars: method chains, expressions, feels like Python
    • DuckDB: SQL, familiar to anyone who took DATASCI 151
  • Many people use both: SQL for the big aggregation, Polars or pandas for the follow-up
  • A DuckDB result converts to either DataFrame with one method:
    • .df() gives a pandas DataFrame
    • .pl() gives a Polars DataFrame
  • So you can write the heavy query in SQL and continue in whichever library you prefer
  • The same hand-off pattern we saw with Polars
q = """
    SELECT indicator, AVG(value) AS mean_value
    FROM '../lecture-19/data/wdi_panel.parquet'
    WHERE year >= 1990
    GROUP BY indicator
"""

# To pandas
pdf = duckdb.sql(q).df()

# To Polars
pol = duckdb.sql(q).pl()

type(pdf), type(pol)
(pandas.DataFrame, polars.dataframe.frame.DataFrame)

Want more SQL practice? The course website has a full self-study DuckDB SQL tutorial. It covers SELECT, WHERE, GROUP BY, joins, and window functions with DuckDB, for anyone who skipped DATASCI 151 or wants more depth

Reading the benchmark honestly

  • Every benchmark measures one task on one machine
  • Treat the numbers as evidence about this setting, and expect them to shift with:
    • the task (this one is a simple aggregation)
    • the hardware (cores, RAM, disk speed)
    • the data shape and file layout
  • What stays the same:
    • The order of magnitude: Polars and DuckDB are far ahead for single-node analytics
    • The zero setup cost: no cluster, no config
  • The order of magnitude is the result worth remembering; the exact seconds will differ on your machine

Which tool when? 🧭

A decision framework

What we have been building

Your situation Reach for
Fits in RAM, quick exploration, plotting pandas
Big single file or many files, one machine Polars or DuckDB (expressions or SQL, your preference)
Bigger than the machine, a real cluster, or task graphs / arrays Dask (or Spark in industry)

pandas → Polars/DuckDB → Dask

  • When Dask still wins:
    • Data larger than one machine’s disk
    • A real cluster of many machines
    • Parallel arrays and custom task graphs (the dask.delayed pipelines from last lecture)
  • Fast single-machine engines shrink the set of problems that need Dask. The cases above remain genuinely distributed
  • pandas is still the right default for small data and for the huge ecosystem around it
  • Polars and DuckDB answer “my data got big and still fits on one machine”
  • From last lecture, before you scale anything:
    • Amdahl first: measure where the time goes
    • A better algorithm or a faster engine often beats adding cores

A word on GPUs

When different hardware is worth the trouble

  • Everything today used your CPU, which are general-purpose processors with a few fast cores
  • A GPU has thousands of small, slow cores
  • That suits data-parallel work
    • The same operation applied to millions of numbers at once, like matrix multiplication
  • This is exactly what training a neural network needs
  • GPUs pay off when the work is the same arithmetic repeated across millions of values
  • Ordinary data wrangling rarely has that shape, which is why everything else today ran on the CPU
  • For data analysis, the GPU stack is RAPIDS, renamed CUDA-X in August 2026:
    • cuDF: DataFrames on the GPU
    • cuML: the same offer for scikit-learn

Source: NVIDIA CUDA-X

GPUs without rewriting your code

  • cudf.pandas accelerates pandas from one line
    • %load_ext cudf.pandas in a notebook
  • It covers the whole pandas API and falls back to the CPU, so your code still runs
  • The Polars GPU engine does the same for lazy Polars
    • You pass an engine to collect, and unsupported queries fall back to the CPU
  • It is still open beta, and NVIDIA aims it at datasets of hundreds of gigabytes and up
  • No GPU on your laptop? Google Colab gives you one for free, and both projects ship a Colab demo
  • Nothing in the final project needs a GPU

Appendix 03: When something goes wrong

No buffer space available

The cluster ran out of network resources for worker-to-worker traffic. Use a smaller array, or lower n_workers and threads_per_worker.

Stream is closed or CommClosedError

A worker died mid-computation, usually in an interactive terminal. Run the same code from a script or a Jupyter notebook instead.

The dashboard will not open

The port is already taken. Pick a free one with dashboard_address=':8789', or let Dask choose automatically.

Workers keep restarting

This is memory pressure. Lower n_workers, raise the memory limit, or process the data in smaller chunks.

The computation hangs

You probably created two clients. Restart the kernel and create exactly one Client

General advice: create one Client at the top of your script and reuse it. Watch the task stream and worker memory panels on the dashboard, and when in doubt restart the client and run on a smaller sample first
